# 多机对抗与自然语言场景生成 · 实施计划

本文件把两项功能拆成可落地的阶段：**多机对抗**（N vs M，总机数 ≤ 8）与**自然语言生成空战场景**（文本 → 配置 → 仿真）。
阶段顺序沿用评审建议：P0 → P1 → P2 → P3 → P5/P6（可与 P2 并行）→ P4 → P7。

---

## 1. 目标与范围

### 1.1 功能目标

1. **多机对抗**：一个场景内可配置 2–8 架飞机，分属两个阵营；支持战斗机、拦截机、轰炸机、护航机四类角色；按团队判定胜负。
2. **自然语言场景生成**：输入中文作战描述，自动生成可运行的 scenario 配置并执行仿真，例如：
   > “现有敌方两架 F-15E 正奔向我方某坐标执行轰炸任务，现命令起飞两架 J-20 进行拦截，将敌方阻止在 JDAM 打击范围外。”

### 1.2 硬约束

- **全场飞机总数 ≤ 8**（含双方，含轰炸机）。该值在配置加载和 `World` 构造时双重校验，超限直接报错，不做静默截断。
- 保持现有 1v1 场景与平衡结果不回归：2 队各 1 机走原有代码路径，事件与结算文本不变。
- 仿真内核仍为确定性：同一 seed + 同一输入 → 同结果；自然语言解析的随机性必须由 seed 收敛。

## 3. 总体架构

三层职责分离，避免把“任务语义”塞进制导律：

1. **MissionSpec（任务中间表示）**：自然语言解析的唯一产物，JSON 可校验；再由生成器转成 scenario yaml。
2. **TeamBrain（团队决策）**：目标分配、角色分工、开局战术选择；输出每架飞机的“主目标 + 战术意图”。
3. **World（物理与交战）**：多目标感知、火控、导弹、裁判；不关心“为什么打”，只回答“能不能打”。

TacticalAgent 继续作为单机执行器，输入从“唯一 foe”扩展为“主目标 + 接触列表”，内核机动逻辑尽量复用。

## 4. 实施阶段

### P0 机型与任务词汇表（前置）

**任务**

- 新增 `configs/aircraft/f15e.yaml`、`configs/aircraft/j20.yaml`：雷达、RCS（含前/侧/后向）、推重比、挂架、燃油。
- 新增 JDAM 武器配置：投放包线、圆概率误差、对地目标类型。
- 明确 `AircraftSpec` / `WeaponSpec` 的最终字段，尤其 RCS 与传感器字段，后续不再反复改。

**完成标志**

- 新机型可在 1v1 场景中加载并完成一局；`pytest` 全绿。

### P1 多机数据模型（不破坏 1v1）

**schema 扩展（草案）**

```yaml
id: intercept-jdam
time_limit_s: 600
teams:
  - name: BLUE
    mission: {type: intercept, protect: {x: 0, y: 0}, keep_out_radius_m: 25000}
    aircraft:
      - {id: J-20, callsign: Viper1, role: interceptor,
         spawn: {x: -70000, y: -3000, z: 9000, psi: 0.0, v: 420}}
      - {id: J-20, callsign: Viper2, role: interceptor,
         spawn: {x: -70000, y: 3000, z: 9000, psi: 0.0, v: 420}}
  - name: RED
    mission: {type: strike, target: {x: 0, y: 0}, weapon: JDAM}
    aircraft:
      - {id: F-15E, callsign: Eagle1, role: bomber, ...}
      - {id: F-15E, callsign: Eagle2, role: escort, ...}
```

**任务**

- `TeamSpec.aircraft` 支持 `str | list`；新增 `role`、`callsign`、`spawn`、`mission`。
- 新增 `rules`：ROE（`weapons_free` / `weapons_hold`）、交战区、禁射区。
- 校验：总机数 ≤ 8、每队 ≥ 1 机、机型已注册、出生点不重叠且位于空域内。
- `Scenario` 增加 `is_duel` 标志，1v1 继续走旧路径。

**完成标志**

- 旧 yaml 原样可加载；新增 2v2 示例可加载但不要求能打。

### P2 拆除 1v1（核心）

**任务**

- `Observation` 增加 `contacts: tuple[Contact, ...]`（距离、方位、速度、识别、威胁度）；`foe_*` 保留为“主目标”兼容字段。
- 新增 `World._select_target(i, roe)`：按火控接触、发射包线、威胁度、任务角色、友军占位打分；发射时把 `target` 固化到 `Missile`（字段已存在）。
- 雷达/告警/数据链改为逐对计算；`contact` 状态从标量改为按目标维护。
- 裁判改为团队聚合：团队存活数、总血量比例、任务完成度；`result` 用队伍名，1v1 时映射回 `red/blue` 以兼容前端与旧测试。
- 事件文本加呼号，例如 `Viper1 发射 R-77-1 → Eagle1`。

**完成标志**

- 2v2 能跑满时限；无友军误伤；现有 42 项测试与 golden 不变。

### P3 多机战术与角色

**任务**

- `TeamBrain`：威胁排序、火力去重（避免两机打同一目标）、护航绑定（escort 跟随 bomber）、支援分配。
- 轰炸机：waypoint 导航 + 投放条件（进入 JDAM 包线且目标仍在），遭拦截时规避并呼叫护航。
- 最小协同：双机分侧进入；长机接战、僚机保持高度差支援。
- ROE：`weapons_hold` 禁射、禁射区拒射、IFF 校验。

**完成标志**

- 2v2 中轰炸机在护航下完成一次投放；护航机在轰炸机被锁时能脱离并拦截。

### P4 Web 与观战

**任务**

- `build_world` / `build_agents` 支持多机；`server.py` 的 `foe = acs[1-i]` 全部替换为目标/队伍查询。
- HUD 接触列表、队伍配色、呼号名牌、击杀日志、团队结算页。
- 新增 2v2 / 4v4 示例场景，场景选择器按机数标注。

**完成标志**

- 浏览器可完整观战 4v4，队伍颜色与结算正确；性能满足第 6 节指标。

### P5 自然语言 → MissionSpec → yaml（可与 P2 并行）

**任务**

- 定义 `MissionSpec` JSON Schema：阵营、机型与数量、呼号、出生点或空域、任务（拦截/护航/轰炸）、约束（JDAM 半径、时限、禁飞区）、ROE、seed。
- 两条解析路径：
  1. **规则解析器**（离线、必过测试）：机型词典、数量词、方位距离、“阻止在 X 范围外”等句式；
  2. **LLM 解析**（OpenAI 兼容接口，密钥走环境变量）：只允许输出 JSON，schema 校验失败或超时回落规则解析。
- 生成器 `tools/nl_scenario.py`：
  ```bash
  python -m tools.nl_scenario "现有敌方两架 F-15E …" --out configs/scenarios/generated/ --run
  ```
- 生成物默认写入 gitignore 目录，避免污染手写场景。

**完成标志**

- 示例指令能生成 yaml 并跑完一局；含糊输入能得到明确报错，而不是空场景。

### P6 几何可行性求解（决定功能好不好用）

**任务**

- 由敌机起点、目标点、速度推算其进入 JDAM 投放圈的时刻。
- 由我方起飞点、爬升/加速包线推算最早可拦截时刻；反推所需拦截线（距目标 `R_jdam + 余量`）。
- 自动放置我方出生点；若时间/距离不满足，**判定不可行并给出最小可行参数**（提前起飞、增大间距、增加拦截机数量）。

**完成标志**

- “阻止在 JDAM 范围外”的约束在生成阶段被量化验证；不可行输入有可读解释。

### P7 测试、文档与发布

**任务**

- 多机用例：2v2 目标分配、友军不射、团队全灭、超时团队判定、8 机上限校验。
- 自然语言用例：约 20 条中文指令快照（含含糊/矛盾输入），LLM 路径用 mock，规则路径离线跑通。
- 批量实验支持多进程（见第 6 节）。
- 文档：README 场景 schema、`docs/` 新增本计划落地后的使用说明；版本号按第三位递增。

**完成标志**

- `pytest` 全绿；一次 4v4 观战与一次自然语言生成的完整链路可复现。

## 5. 开局战术选择策略（新增）

现有开局只有“角度型 / 能量型”两套占位参数。多机与隐身机型加入后，需要把开局做成**可配置的战术库**，由 TeamBrain 依据装备差、数量、任务选择。

### 5.1 战术库（首版）

| 战术 | 适用条件 | 行为要点 |
| --- | --- | --- |
| `stealth_compress` 隐身压缩 | 我方 RCS 显著低于对手，且携带中距弹 | 雷达静默 + 迎头/小侧偏进入，保持最小 RCS 姿态；靠 AWACS/友机数据链接敌，压缩对方发现距离后再开机 |
| `silent_flank` 静默侧击 | 我方数量劣势但隐身占优 | 大侧偏绕行，避开对方雷达扇区，从侧后方进入 |
| `energy_climb` 能量爬升 | 双方均无隐身优势 | 交汇前换高度，保留能量打垂直机动 |
| `bait_and_punish` 诱敌 | 我方数量占优 | 一架前出诱使对方先射，另一架保持能量待机反击 |
| `escort_tether` 护航绑定 | 我方有轰炸机 | 护航机与轰炸机保持 3–5 km 间隔，优先拦截来袭导弹载机 |
| `drag_defense` 拖曳防御 | 被先手锁定 | 协同转向、干扰弹窗口共享、互相掩护脱离 |

### 5.2 隐身的建模要求

- `AircraftSpec.rcs` 从标量扩展为 **前向 / 侧向 / 后向** 三段（或按方位角的查找表），探测距离按 RCS 的四次方根缩放。
- 新增“被发现距离”指标：`detect_range(own, foe, aspect)`，供战术选择与赛后复盘使用。
- `stealth_compress` 的目标函数：在进入对方火控包线前，把对方雷达接触等级压到“搜索”而非“跟踪”，争取首发。

### 5.3 选择逻辑

`TeamBrain` 在开局 10 s 内完成一次评估并锁定战术，评估输入：

- 双方机型 RCS、雷达探测距离、中距弹数量；
- 数量比、任务类型（拦截/护航/轰炸）；
- 初始几何（迎头角、高度差、距离）。

评估结果写入 `agent.opening_tactic`，并输出到事件日志（`Viper1 选择 stealth_compress`），便于复盘与测试断言。

### 5.4 验收指标

- 同机型的 1v1，隐身机选择 `stealth_compress` 时，对手首次进入“跟踪”的距离应显著小于非隐身机基准。
- 2v2 中，选择 `bait_and_punish` 的一方首发时间晚于对手，但首发命中率更高（用 seed 扫描统计）。

## 6. 传感器复杂度与多核

### 6.1 复杂度

- 逐对传感器/可见性评估为 **O(N²)**：N=8 时 28 对，单帧成本可接受；真正的开销在 120 Hz 内层循环与逐对视线/多普勒计算。
- 结论：**优先向量化，而不是无脑上多进程**。把逐对计算整理成 N×N 矩阵（距离、方位、径向速度、可见度），用 NumPy 一次算完，避免 Python 双重循环与对象属性访问。

### 6.2 多核使用边界

| 场景 | 方案 |
| --- | --- |
| Web 实时观战 | 单进程；不启用进程池，避免 IPC 抖动与 GIL 争用 |
| 无头批量实验（seed 扫描、平衡性统计） | `multiprocessing` 进程池，**一局一进程**，结果回传 JSON；`--workers` 控制核数 |
| 大规模参数扫描 | 任务级并行优先；必要时把 N×N 传感器矩阵按行分块到 worker，仅用于离线分析 |
| 未来单局提速 | 先 profile，再考虑 C 扩展/ numba；不改变确定性 |

关键点：**并行粒度是“局”而不是“帧”**。单局内拆帧会引入同步开销并破坏可复现性。

### 6.3 性能验收

- 8 机 300 s 无头仿真：耗时不超过当前 1v1 单局的 4 倍。
- 4v4 Web 观战：稳定 ≥ 1× 实时（画面不因仿真滞后而卡顿）。
- 批量 16 局（8 机）在 4 核机器上：总耗时明显低于串行（给出实际测量值后写入 README）。

### 6.4 传感器特性待办（IRST 吊舱）

- **IRST 吊舱全向感知**：吊舱可 360° 覆盖（不限于机头前向），但有一定的采样频率（非连续帧），目标在两次采样之间可能移动。需要建模：
  - 全向视场（方位 0–360°，俯仰有限）；
  - 采样周期（如每秒若干帧），采样时刻才有观测，采样间隙目标位置需外推；
  - 探测距离随目标 IR 特征（加力尾焰、迎角、蒙皮温度）与大气衰减变化。
- **状态**：仅登记待办，暂不实现。后续在传感器矩阵（6.1）中加入 IRST 通路时一并建模。

## 7. 验收标准汇总

1. **多机**：2v2、4v4 可跑满时限；无友军误伤；结算按团队；8 机上限生效。
2. **1v1 不回归**：现有测试、golden、CLI 与 Web 行为不变。
3. **自然语言**：示例指令可生成可运行配置；矛盾输入给出不可行原因；规则解析离线可复现。
4. **战术**：`stealth_compress` 的“被发现距离”指标可测量，并在日志中可见。
5. **性能**：满足 6.3 的三条指标。

## 8. 风险与待决问题

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| TacticalAgent 与 `foe_*` 深耦合 | 直接改会破坏现有平衡 | 保留 1v1 快路径；先加接触列表，再逐步迁移 |
| 机型参数来源 | F-15E / J-20 / JDAM 数据需要可信出处 | P0 先定字段与口径，参数标注来源与置信度 |
| LLM 输出不稳定 | 自由文本可能生成非法配置 | JSON Schema + 规则兜底 + 固定 seed，三者缺一不可 |
| 多核收益有限 | 单局内并行得不偿失 | 并行粒度锁定为“局”；单局先向量化 |
| 任务判定歧义 | “阻止在 JDAM 范围外”如何算成功 | 明确为“敌机进入投放圈前被击落/驱离”，写入 schema 与结算文本 |
