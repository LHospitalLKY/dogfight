# 多机对抗与自然语言场景生成 · 实施计划

本文件把两项功能拆成可落地的阶段：**多机对抗**（N vs M，总机数 ≤ 8）与**自然语言生成空战场景**（文本 → 任务中间表示 → scenario yaml → 仿真）。
阶段顺序：P1 → P2 → P3 → P4 → P5（可与 P2 并行）→ P6。原 P0（机型库 / 分向 RCS / 开局战术骨架）已基本落地，剩余项并入对应阶段。

> **本版范围：只做空空对抗。** 对地轰炸相关（bomber / escort 角色、JDAM、投放几何与命中判定）全部移出本计划，后续单独立项；因此本版不包含“几何可行性求解”阶段。

> 状态基线：本计划对应 `68 passed` 的测试集（`tests/test_*.py` + `tests/golden/seed3.json`）。所有阶段的“完成标志”都以不回归该基线为前提。

## 1. 目标与范围

### 1.1 功能目标

1. **多机对抗**：一个场景内可配置 2–8 架飞机，分属两个阵营；首版支持战斗机 / 拦截机两类角色（轰炸机与护航机随对地任务单独立项）；按团队判定胜负。
2. **自然语言场景生成**：输入中文作战描述，自动生成可运行的 scenario 配置并执行仿真，例如：
   > “现有敌方两架 F-15E 沿 NE 航向接近我方某坐标，现命令起飞两架 J-20A 进行拦截，将敌机阻止在 25 km 保护空域之外。”

### 1.2 硬约束

- **全场飞机总数 ≤ 8**（含双方）。该值在配置加载和 `World` 构造时双重校验，超限直接报错，不做静默截断。
- **1v1 不回归**：两 队各 1 机继续走现有快路径，事件文本、结算字段、CLI 与 Web 行为、`tests/golden/seed3.json` 全部不变。
- **确定性**：同一 seed + 同一输入 → 同一结果；自然语言解析的随机性必须由 seed 收敛。
- **并行粒度是“局”不是“帧”**：单局内不拆帧并行，避免破坏可复现性（见 6.2 节）。

## 3. 总体架构

三层职责分离，避免把“任务语义”塞进制导律：

1. **MissionSpec（任务中间表示）**：自然语言解析的唯一产物，JSON Schema 可校验；再由生成器转成 scenario yaml。它只描述“谁、在哪、做什么、受什么约束”，不描述物理。
2. **TeamBrain（团队决策）**：目标分配、角色分工、开局战术选择、火力去重；输出每架飞机的“主目标 + 战术意图 + 角色”。运行在 1–2 Hz，不进 120 Hz 内层循环。
3. **World（物理与交战）**：多目标感知、火控、导弹、裁判；不关心“为什么打”，只回答“能不能打、打到没有”。

`TacticalAgent` 继续作为单机执行器，输入从“唯一 foe”扩展为“主目标 + 接触列表 + 团队意图”，其内核机动逻辑（BVR 占位、防御、近距缠斗）尽量复用。1v1 时 `contacts` 退化为单元素，`foe_*` 兼容字段保持不变。

## 4. 实施阶段

### P1 多机数据模型（不破坏 1v1）

**schema 扩展（草案）**

```yaml
id: intercept-2v2
time_limit_s: 600
teams:
  - name: BLUE
    mission: {type: intercept, protect: {x: 0, y: 0}, keep_out_radius_m: 25000}
    aircraft:
      - {id: J-20A, callsign: Viper1, role: interceptor,
         spawn: {x: -70000, y: -3000, z: 9000, psi: 0.0, v: 420}}
      - {id: J-20A, callsign: Viper2, role: interceptor,
         spawn: {x: -70000, y: 3000, z: 9000, psi: 0.0, v: 420}}
  - name: RED
    mission: {type: sweep}
    aircraft:
      - {id: F-15E, callsign: Eagle1, role: fighter,
         spawn: {x: 70000, y: -3000, z: 9500, psi: 3.1416, v: 430}}
      - {id: F-15E, callsign: Eagle2, role: fighter,
         spawn: {x: 70000, y: 3000, z: 9500, psi: 3.1416, v: 430}}
```

**任务**

- `TeamSpec.aircraft` 从 `AircraftEntry` 改为 `list[AircraftSlot]`；`AircraftSlot` 含 `id / callsign / role / spawn / loadout / radar_policy / opening_tactic`。保留“`aircraft` 可写单个字符串”的 1v1 简写，加载时归一化为单元素列表。
- `Scenario` 增加 `is_duel` 标志（两队各 1 机 → `True`，走旧快路径）。
- 新增 `rules`：ROE（`weapons_free` / `weapons_hold`）、交战区 / 禁射区多边形、`keep_out_radius_m`（保护空域半径）。
- 加载期校验：总机数 ≤ 8、每队 ≥ 1 机、机型已注册、出生点不重叠且位于空域内、呼号唯一、`role` ∈ {fighter, interceptor}。
- `World` 构造期二次校验总机数，超限抛 `ConfigError`，不静默截断。

**完成标志**

- 旧 yaml（`aircraft` 单字符串、无 `role` / `callsign` / `spawn`）原样可加载，行为不变。
- 新增 2v2 示例 yaml 可加载（不要求能打）；`is_duel` 判定正确。
- 越限（9 机）、出生点重叠、未知 role 均有明确报错。

### P2 拆除 1v1（核心，P1 之后立即做）

**任务**

- `Observation` 增加 `contacts: tuple[Contact, ...]`，`Contact` 含：目标索引、距离、方位、径向速度、识别（敌我）、接触等级（未发现 / 搜索 / 跟踪 / 火控）、威胁度。`foe_*` 系列保留为“主目标”兼容字段，由 `contacts` 中当前主目标回填。
- 新增 `World._select_target(i, roe) -> int | None`：按火控接触、发射包线（NEZ）、威胁度、任务角色、友军占位打分；命中选择后把 `target` 固化到 `Missile`（`Missile.target` 字段已存在）。
- 雷达 / 告警 / 数据链改为逐对（N×N）计算；`contact` 状态从标量改为按目标维护。先保持 Python 逐对循环跑通正确性，向量化留到 P6 性能阶段。
- 裁判改为团队聚合：团队存活数、团队总血量比例、任务完成度（敌机是否在进入保护空域前被击落 / 驱离）；`result.winner` 用队伍名，1v1 时映射回 `red/blue` 以兼容前端与旧测试。
- 事件文本加呼号：`Viper1 发射 PL-15 → Eagle1`，而非“红方发射”。
- 友军误伤防护：`_select_target` 排除己方目标；导弹引信/近炸只对敌方触发；保留一条“误射友军”测试断言其不发生。

**完成标志**

- 2v2 能跑满时限；无友军误伤；现有 68 项测试与 `tests/golden/seed3.json` 不变。
- 击杀 / 坠机 / 越界 / 超时均按团队结算，事件日志带呼号。

### P3 多机战术与角色

**任务**

- 新增 `TeamBrain`（可放在 `dogfight/tactics/team.py`）：
  - 威胁排序：按敌方距离、朝向、是否带弹、离保护空域的距离打分。
  - 火力去重：避免两机同时锁定 / 发射同一目标（除非目标剩余血量需要 >1 发）。
  - 支援分配：长机接战时僚机保持高度差 / 侧向占位；一机被锁定时另一机反制。
- 角色行为：`interceptor` 优先拦截突入保护空域的敌机；`fighter` 争夺制空、压制对方带弹机。
- 最小协同：双机分侧进入；长机接战、僚机保持能量支援。
- ROE 落地：`weapons_hold` 禁射、禁射区拒射、IFF 校验（数据链 / 预警机识别）。
- 补全开局战术库中与多机相关的条目（见第 5 节）：`bait_and_punish`、`drag_defense`。

**完成标志**

- 2v2：双机能分侧接敌，僚机在长机被锁时进入支援；无友军误伤。
- ROE `weapons_hold` 下全场零发射；禁射区拒射生效。
- 至少一个 2v2 seed 扫描统计可复现（写入 `experiments/`）。

### P5 自然语言 → MissionSpec → yaml（可与 P2 并行）

**任务**

- 定义 `MissionSpec` JSON Schema（放在 `dogfight/config/mission_spec.py` 或 `tools/nl/schema.json`）：阵营、机型与数量、呼号、出生点或空域、任务类型（intercept / sweep）、约束（保护空域半径、时限、禁飞区）、ROE、seed。
- 两条解析路径：
  1. **规则解析器**（离线、必过测试）：机型词典、数量词、方位距离、“阻止在 X 范围外”“保护目标”“分侧进入”等句式；输出 `MissionSpec`。
  2. **LLM 解析**（OpenAI 兼容接口，密钥走环境变量 `DOGFIGHT_LLM_KEY` 等）：只允许输出 JSON，schema 校验失败或超时 → 回落规则解析。LLM 温度固定为 0，结果由 seed 收敛。
- 生成器 `tools/nl_scenario.py`：
  ```bash
  python -m tools.nl_scenario "敌方两架 F-15E 沿 NE 航向接近我方坐标，起飞两架 J-20A 拦截" \
      --out configs/scenarios/generated/ --run --seed 42
  ```
- 生成物默认写入 gitignore 目录（`configs/scenarios/generated/`），避免污染手写场景；`--run` 直接跑一局并打印结算。
- 错误处理：含糊 / 矛盾输入（如机型不存在、保护空域半径小于初始间距导致拦截线在起点之后）给出明确报错，而不是生成空场景。

**完成标志**

- 示例指令能生成 yaml 并跑完一局；规则解析路径离线可复现（无网络、无密钥）。
- LLM 路径用 mock 测试：schema 合法 → 通过；非法 → 回落规则；超时 → 回落。

## 5. 开局战术库（现状与扩展）

现有开局已有 `default` / `stealth_compress` / `flank` 三套（`flank` 对应原计划的 `silent_flank` 的单机版），由 `TacticalAgent` 单机执行。多机与隐身机型加入后，需要：

1. 把**单机占位战术**（已实现）与**团队协同战术**（待实现）分开：前者由 `TacticalAgent` 执行，后者由 `TeamBrain` 编排。
2. `TeamBrain` 在开局 10 s 内完成一次评估并锁定团队战术，评估输入：双方机型 RCS、雷达探测距离、中距弹数量、数量比、任务类型、初始几何。结果写入事件日志（`BLUE 选择 bait_and_punish`），便于复盘与测试断言。

## 6. 传感器复杂度与多核

### 6.1 复杂度

- 逐对传感器 / 可见性评估为 **O(N²)**：N=8 时 28 对，单帧成本可接受；真正的开销在 120 Hz 内层循环与逐对视线 / 多普勒计算。
- 结论：**优先向量化，而不是无脑上多进程**（P6 执行）。把逐对计算整理成 N×N 矩阵（距离、方位、径向速度、可见度），用 NumPy 一次算完，避免 Python 双重循环与对象属性访问。

### 6.2 多核使用边界

| 场景 | 方案 |
| --- | --- |
| Web 实时观战 | 单进程；不启用进程池，避免 IPC 抖动与 GIL 争用 |
| 无头批量实验（seed 扫描、平衡性统计） | `multiprocessing` 进程池，**一局一进程**，结果回传 JSON；`--workers` 控制核数 |
| 大规模参数扫描 | 任务级并行优先；必要时把 N×N 传感器矩阵按行分块到 worker，仅用于离线分析 |
| 未来单局提速 | 先 profile，再考虑 C 扩展 / numba；不改变确定性 |

关键点：**并行粒度是“局”而不是“帧”**。单局内拆帧会引入同步开销并破坏可复现性。

### 6.3 性能验收（P6）

- 8 机 300 s 无头仿真：耗时不超过当前 1v1 单局的 4 倍。
- 4v4 Web 观战：稳定 ≥ 1× 实时（画面不因仿真滞后而卡顿）。
- 批量 16 局（8 机）在 4 核机器上：总耗时明显低于串行（实测值写入 README）。

### 6.4 传感器特性待办（IRST 吊舱，仅登记）

- **IRST 吊舱全向感知**：吊舱可 360° 覆盖（不限于机头前向），但有采样频率（非连续帧），目标在两次采样之间可能移动。需要建模：
  - 全向视场（方位 0–360°，俯仰有限）；
  - 采样周期（如每秒若干帧），采样时刻才有观测，采样间隙目标位置需外推；
  - 探测距离随目标 IR 特征（加力尾焰、迎角、蒙皮温度）与大气衰减变化。
- **状态**：仅登记待办，暂不实现。后续在传感器矩阵（6.1）中加入 IRST 通路时一并建模。

### 9.4 PURE 追踪修复（P3.2）

**问题与根因**

1. 尾追时后机转弯半径过大：`pursuit_action` 把总过载收口在 `max(n_sustain×1.25, 2 g)`。250 m/s 下 J-16 可用过载 9 g，实际只拉 5.2 g，理论半径 1 250 m 对 790 m。
2. PURE 俯仰抖动：目标在侧方且偏下时，`a < PUSH_ENTER` 触发翼平推杆，推杆保持结束后又压回 86° 坡度；实测指令在 `n=-0.9` 与 `n=+1.6` 之间以 0.3–0.5 s 周期翻转。

**修改**

- `pursuit_action` 新增 `max_load` 参数；PURE 使用可用过载（受升力/结构限制），速度下降后 `own_n_avail` 自然收敛。
- 推杆只在目标位于机头 ±50° 内时允许；目标在侧方时保持大坡度拉杆，用 `n·cosφ` 产生下俯，不再在推杆/拉杆间横跳。
- 新增回归测试：可用过载释放、侧方偏下目标不推杆。

**验证**

- 受控尾追：指令过载 5.2 g → 8.1 g，航向角速度 −8°/s → −15°/s，转弯半径约减半。
- 2v2 seed=3 全程 PURE 期间过载符号翻转：Flanker1 0 次、Flanker2 2 次（间隔 2 s，属正常过渡）、Shark1/2 0 次；最低速度 189 m/s，未失速。
- `pytest` 94 项全绿；1v1 行为随 PURE 修复变化，`tests/golden/seed3.json` 已重新生成并校验一致。

- 机体/导弹按视深缩放到约 64 px 的屏幕长度（倍率限制在 1–40 倍，检视模式仍为 1:1）：全程都能看清完整模型，又不会在远距放大成互相穿插的巨物；只有倍率封顶后投影仍短于 12 px 时才改用细长的扁平箭头。

### 9.7 场景背景与开场编队掷骰

- 场景新增 `brief`（HUD 左上显示的战术背景）与每队 `side`（attacker / defender）；默认第一队进攻、第二队防守。
- 每队新增 `formation_group` 编队池，开局按种子随机抽一种；Web 端每开一局重新掷（`--seed` 时结果可复现），库层不带种子时固定按 0 掷，保证测试可复现。
- 内置 12 种队形：横队、梯队、纵队、疏散、阶梯、叠型、战斗僚机、指尖四机、流动四机、盒形、箭头、楔形；解析时校验该队形是否支持本队机数，未知或不支持会直接报错。
- 出生点改为“队首固定在基准点，其余按队形排在队首后方”，双方仍在 `initial.spacing_m` 处对头进入。
- 编队池：进攻方 2v2 为梯队/战斗僚机/疏散，4v4 为梯队/指尖四机/流动四机/楔形；防守方 2v2 为梯队/疏散，4v4 为梯队/盒形/箭头。横队与纵队已从作战编队池移除，纵队仅保留给着陆等需要单列跟飞的场合。
- HUD 左上显示 `red 进攻 · 楔形 ｜ blue 防守 · 盒形` 与 `brief`；多机时该面板自动下移到顶部名册下方，避免遮挡。
- 验证：`pytest` 98 项全绿、golden 基线一致；浏览器实测 4v4 抽到楔形 / 盒形，名册、文案与布局正常，控制台无错误。

### 9.8 四机指挥结构、目标决策与克制发射

- 四机军阶改为 `flight_lead / wingman / element_lead / wingman`：中队长（flight_lead）兼任第一双机小队长，第 3 机为第二双机小队长，各带一架僚机；`TeamBrain._elements()` 据此配对。
- 中队长每拍按目标数决策：目标数多于双机数时分头接战，收拢到双机数以内或出现重伤目标时集中火力；切换带 12 s 驻留，避免目标数抖动导致来回切。事件日志输出“中队长决定集中火力 / 分头接战”。
- 克制发射：同一目标只保留一名主射手（接战角色 → 军阶 → 入队顺序）；已有一枚本队导弹在飞且目标血量高于 50% 时不再齐射；目标重伤后允许下一架补刀。中距弹与格斗弹分别去重。
- Web `SimEngine` 在多机场景接入 `TeamBrain`：每个决策拍先 `plan()` 再 `filter_actions()`；1v1 与纯追踪基线不启用，保持原平衡与可复现性。
- 移除界面残留的开火/高 G 菱形标记，以及发射点、箔条、热诱弹的点标记；干扰物只保留云团/火球动效。
- 验证：`pytest` 103 项全绿、golden 基线一致；4v4 开局日志显示中队长决定分头接战，每架飞机每个目标每次只由一架发射。
